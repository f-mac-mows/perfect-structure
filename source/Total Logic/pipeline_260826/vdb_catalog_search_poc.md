# VDB(임베딩 카탈로그) 검색 - 설계/검증/다음 단계 (2026-08-19)

## 0. 요약

- **검증됨(작게)**: KOSIS 표 제목을 CLOVA embedding으로 벡터화해서 sqlite-vec에
  저장하고, claim 텍스트를 실시간 임베딩해서 코사인/L2 유사도로 가까운 표를
  찾는 경로 — 키워드가 하나도 안 겹치는 패러프레이즈 claim에서도 정답 표가
  top-5 안에 들어오는 걸 18개 표 규모로 확인했다.
- **아직 안 풀린 것(이번 세션에서 새로 발견)**: "표를 찾는 것"과 "그 표 안에서
  어떤 항목/분류값이 claim에 해당하는지 고르는 것"은 완전히 다른 두 단계인데,
  지금 VDB는 1단계(표 발견)만 다룬다. 2단계(표 확정 후 내부 항목/축 매칭)는
  여전히 순수 문자열 부분일치뿐이라, "나랏빚"으로 "국가채무" 표까지는 찾아도
  그 표 안의 실제 컬럼명("국가채무", "GDP대비비율" 등)과 "나랏빚"이 문자로
  안 겹치면 그 다음 단계에서 그대로 막힌다. **이게 이번 논의에서 확인한, 다음에
  풀어야 할 핵심 갭이다.**

## 1. 왜 이 작업을 시작했나

기존 파이프라인(1번 claim 추출 → 2번 임베딩 기반 검색어 증폭 → 3번 KOSIS
키워드 검색 → 4번/5번 이 레이어의 표 확정+판정)의 구조적 한계: 3번이 KOSIS에
날리는 검색어 자체가 KOSIS의 공식 표 제목/용어와 문자 그대로 안 겹치면
애초에 후보 표가 하나도 안 나온다("나랏빚"이 "국가채무"라는 KOSIS 공식
용어와 전혀 안 겹치는 경우 등). 2번(검색어 증폭)도 3번(KOSIS 검색)도 결국
"어떤 표를 찾을지" 단계에서 이 문제를 풀려는 시도이고, VDB(로컬에 KOSIS
카탈로그를 미리 임베딩해두고 의미 유사도로 찾는 것)는 같은 문제에 대한
또 다른 접근이다 - 서로 대체재이지 순서상 이어지는 게 아니다.

## 2. 실제로 만든 것

| 구성요소 | 파일 | 상태 |
|---|---|---|
| catalog_titles/catalog_vec 스키마 | `kosis_warehouse.py` | 기존(2026-08-17 설계, 이번에 처음 실제 씨딩) |
| KOSIS 카탈로그 크롤러 | `kosis_warehouse.crawl_catalog()`, `client.get_statistics_list()` | 기존, 실측 완료(`probe_statistics_list.py`) |
| sqlite-vec 통합(벡터 저장/검색) | `vdb_discovery.py` | 기존 설계, 이번에 처음 실행 검증 |
| CLOVA embedding 클라이언트 | `embedding_client.py` | 기존(2번 작성) |
| **씨딩 실행 스크립트** | `seed_catalog_vdb.py` | **신규(이번 세션)** |
| **검색 검증 스크립트** | `test_catalog_vec_query.py` | **신규(이번 세션)** |

### 이번 세션에 발견/수정한 버그 3개

1. **`embedding_client.py`의 `.env` 경로 버그**: `PROJECT_ROOT = Path(__file__).resolve().parent.parent`가
   `e2e/`보다 한 단계 위를 가리켜서 `NCP_CLOVASTUDIO_API_KEY`를 못 찾고 있었다
   (`embedding_ranker.rank_keywords`는 실패 시 조용히 기존 순서로 폴백하므로,
   2번의 임베딩 기반 키워드 순위 매기기가 계속 무력화돼 있었을 가능성이 있다).
   `.parent`로 수정 완료.
2. **`client.get_statistics_list`의 진단 정보 부족**: KOSIS가 rate limit 등
   오류일 때 HTTP 200 + `{"err":..., "errMsg":...}` 형태(list가 아닌 dict)로
   응답하는데, 이걸 조용히 `[]`로 삼켜서 원인을 전혀 알 수 없었다. 이제 list가
   아닌 응답은 그대로 로그에 남긴다.
3. **국제기구 표 혼동이 VDB 경로엔 안 걸려 있었음**: `search_local()`은 이미
   `is_international_survey()`로 국제기구 표(IMF/OECD 등)에 감점을 주는데,
   `search_catalog_vec()`은 그 판별에 필요한 `vw_cd`/`stat_nm`을 아예 안 갖고
   있었다. `vdb_discovery.rerank_international_penalty()` 신규 추가로 해결
   (실측: "가계가 실제로 쓰는 품목 기준으로 물가" 질의에서 `DT_2IFS002`(IMF
   국제 소비자물가지수)가 1위로 튀어나오던 게 수정 후 후순위로 밀림).

## 3. 실측 결과

### 3.1 카탈로그 규모/노이즈 (KOSIS 9개 도메인 전체 크롤 시도)

- 90건 claim 도메인과 겹치는 9개 최상위 카테고리(물가/노동/정부재정/금융/
  문화여가/인구/국민계정/소득소비자산/무역국제수지)를 전체 크롤 시도.
- KOSIS 자체 제한(분당 200콜)과 CLOVA embedding rate limit에 둘 다 걸려서
  **인구(2011건)+노동(1571건) 두 도메인만 성공**, 나머지 7개는 실패(재시도해도
  같은 rate limit).
- **노이즈 확인**: `rec_tbl_se`("추천표" Y/N) 필드로 걸러내려 했으나 3582건 중
  Y가 13건뿐이라 필터로 못 쓴다. 실제 데이터를 보면 같은 개념이 지역단위
  (시군구/시도/읍면동)·연령단위(각세/5세별)만 바꿔가며 5~7개씩 별도 표로
  쌓여 있는 패턴이 흔함(예: "전국 직업/성별 취업자(소분류)" 등 7건 동일
  제목). → **9개 도메인 전체를 그대로 임베딩하는 건 시간 대비 비효율이 크다고
  판단, 스코프를 대폭 축소함.**

### 3.2 소규모 검증 (tables_registry의 기존 18개 표만 임베딩)

`seed_catalog_vdb.py --from-registry`로 이미 검증된 18개 표만(신규 KOSIS
호출 없이) 백필+임베딩. `test_catalog_vec_query.py`로 키워드 겹침이 전혀
없는 패러프레이즈 질의 3개 테스트:

| 질의 | 의도한 정답 표 | 결과 |
|---|---|---|
| "청년층의 구직 활동 참여가 둔화되고 있다는 지적이 나온다" | 성/연령별 경제활동인구 | 1위 "연령별 경제활동상태"(밀접한 유사 표), 3위 정답 표 - 둘 다 사실상 맞는 방향, 단 2위에 무관한 "학생 독서활동 실태"가 끼어듦 |
| "가계가 실제로 쓰는 품목 기준으로 최근 물가 오름세를 따져봤다" | 지출목적별/품목성질별 소비자물가지수 | 국제기구 필터 적용 후: 1~4위 전부 국내 CPI 관련 표(등락률/품목성질/지출목적), 국제표는 후순위로 밀림 |
| "상품과 서비스 성격별로 가격이 얼마나 뛰었는지 살펴봤다" | 품목성질별 소비자물가지수 | 1위는 무관한 "국내판매액 변동현황", 정답은 4위 |

**결론**: 키워드가 하나도 안 겹쳐도 정답 표가 top-5 안에는 계속 들어온다
(recall 목적엔 부합) - 단 1위가 항상 정답은 아니다(precision은 낮음, 18개
소규모 표본에서도 무관한 표가 상위권에 끼어드는 경우가 나옴). **즉 이
경로는 "후보를 넓혀주는 역할"까지만 신뢰할 수 있고, 그 후보 중 진짜 정답을
고르는 건 여전히 기존 항목/축 확정 로직에 맡겨야 한다.**

- 규모를 더 키웠을 때(9개 도메인 전체 등) precision/noise가 어떻게 변하는지는
  **미검증** - 다음에 실측 필요.

## 4. 놓치고 있던 것 - 표 발견과 항목/축 확정은 다른 문제다

이번 논의에서 명확해진 것: 파이프라인은 실제로 두 단계다.

1. **표 발견(Table Discovery)** - "이 claim이 어느 통계표 얘기인가"
   - 기존 경로: 2번(임베딩 검색어 증폭) → 3번(KOSIS 키워드 검색, `search_metadata`)
   - 이 레이어 경로: `kosis_local_search.search_local()`(로컬 FTS+표이름 매칭)
   - **이번에 추가한 VDB**: `vdb_discovery.search_catalog_vec()`(표 제목 임베딩 유사도)
   - 셋 다 "어떤 표인가"를 좁히는 게 목적 - 서로 대체/보완재.

2. **항목/축 확정(Column Resolution)** - "그 표 안에서 어떤 항목(ITEM)/
   분류값(축)이 이 claim에 해당하는가"
   - 유일한 경로: `kosis_local_search.resolve_evidence_by_flat_match()` -
     claim의 match_phrases를 그 표의 item/축 breadcrumb 텍스트에 **순수
     문자열 부분일치**로만 매칭한다. 의미 유사도가 전혀 없다.

**문제**: 1단계가 임베딩으로 "나랏빚" → "국가채무" 표를 잘 찾아도, 2단계는
여전히 문자열 매칭뿐이라 그 표의 실제 컬럼명(예: "국가채무", "GDP대비
국가채무비율", "관리대상채무" 등)과 "나랏빚"이라는 단어가 문자로 안
겹치면 그대로 실패한다(`item_candidates`가 비어 `UNVERIFIED_UNRESOLVED`로
빠짐). **이건 VDB를 도입하기 전부터도 이미 존재했을 문제** - 오늘 90건
재검증에서 본 "표는 찾았지만 항목/축 확정 못함" 케이스들 중 상당수가 실은
이 2단계 문제였을 가능성이 크다(표 자체는 FTS로 잘 찾았는데도 발생했으므로).

## 5. 다음 단계 제안 (미구현 - 설계만)

1단계에서 쓴 것과 같은 패턴을 2단계에도 한 번 더 적용한다:

- **범위**: 표가 이미 확정된 뒤이므로, 그 표 하나의 item/축 이름 전체
  (보통 수십~수백 개)만 임베딩하면 된다 - 오늘 겪은 "카탈로그 전체(수천 건)
  임베딩"보다 훨씬 작고 빠르고, rate limit 위험도 낮다.
- **트리거 조건**: `resolve_evidence_by_flat_match`가 `item_candidates`를
  하나도 못 찾았을 때(현재 `query_status="unresolved"`로 빠지는 그 지점)만
  이 임베딩 폴백을 타면 된다 - 문자열 매칭이 되는 경우엔 지금처럼 그대로
  쓰고, 안 될 때만 추가 비용을 쓰는 구조.
- **필요 작업**:
  1. 표별 item/축 이름 목록을 임베딩해서 저장할 곳 결정(표마다 별도
     캐시 - `dimensions` 테이블에 이미 있는 name들을 그대로 재사용 가능,
     새 크롤 불필요).
  2. `resolve_evidence_by_flat_match`가 빈 결과를 낼 때 claim
     match_phrases(또는 raw_sentence)를 임베딩해서 그 표의 item/축
     임베딩과 유사도 비교하는 폴백 함수 추가.
  3. 문자열 매칭 때와 마찬가지로 disambiguate_by_value(값 기반 재검증)를
     그대로 재사용해서, 임베딩으로 좁힌 후보들 중에서도 "확신 있게 하나로
     못 고르면 추측하지 않는다"는 이 프로젝트의 원칙(Decision 003)을
     유지해야 한다.
- **역할 경계 재확인**: 이 2단계 작업은 2번/3번의 몫이 아니다 - 2번/3번은
  "어떤 표인가"만 다루고, "표 안의 어떤 컬럼인가"는 처음부터 이 레이어
  (4번+5번)의 책임이었다. VDB를 표 발견에 쓰든 안 쓰든 이 갭은 이미 있었고,
  이번에 명확히 드러난 것뿐이다.

## 6. 참고 - 재현/확장 방법

```bash
# tables_registry의 검증된 표만 백필+임베딩(권장, 노이즈 없음, 빠름)
python3 seed_catalog_vdb.py --from-registry

# 검색이 실제로 통하는지 확인
python3 test_catalog_vec_query.py "임의의 패러프레이즈 claim 텍스트"

# (당분간 비권장) 9개 도메인 전체 크롤 - rate limit/노이즈 문제로 시간이 오래 걸림
python3 seed_catalog_vdb.py            # 크롤+적재+임베딩 전부
python3 seed_catalog_vdb.py --skip-crawl  # 크롤 생략, 임베딩만 이어서
```

DOMAIN_CODES(9개 도메인 코드)는 `seed_catalog_vdb.py` 상단에 있음 - 필요시
늘리면 되지만, 늘리기 전에 §3.1의 노이즈 문제(같은 개념의 지역/연령 변형이
표마다 별도로 쌓이는 것)를 먼저 어떻게 줄일지 정하는 게 좋다(예: 표 이름
정규화 후 그룹당 1개만 임베딩, 또는 KOSIS의 다른 큐레이션 신호를 찾는 것 -
`rec_tbl_se`는 이미 못 쓴다고 확인됨).
